# v0.4.2 Release Preparation Design

## Context

Remote `main` contains the complete P0/P1 safety scope through merge commit
`34d9db64df652c210177919f32d949aadaf1ba1c`, but the source and generated
artifact still declare immutable version `0.4.1`. Tagging that commit as
`v0.4.2` would fail the release workflow's tag-to-artifact version check.

The owner approved a minimal version-bump commit before tagging. The owner also
waived the audit-only pilot as a release prerequisite. The pilot remains
owner-deferred and must not be recorded as PASS.

## Goal

Prepare the current `main` safety scope as immutable artifact version `0.4.2`,
merge the preparation through a reviewed PR, and publish annotated tag
`v0.4.2` on the resulting `main` merge commit.

## Scope

Create branch `release/v0.4.2` from the current `origin/main` and update:

- The immutable artifact version and its runtime integrity assertion.
- Build, unit, installer, report, and integration expectations that assert the
  current executable version.
- Current-release badges, download commands, interface headings, and release
  candidate statements in user and operator documentation.
- The release integration ledger to record the explicit owner waiver without
  claiming that the audit-only pilot passed.

Historical compatibility text that identifies old `v0.4.1` sample schemas
must remain `v0.4.1`; those references describe data migration boundaries,
not the current release version.

## Delivery Flow

1. Implement the version and documentation updates on `release/v0.4.2`.
2. Run static checks, the complete unit suite, the fast gate, the production
   build/version check, and MariaDB 10.6/11.4 integration.
3. Push the branch, open a PR into `main`, and require green `quality` and
   `integration` checks before merge.
4. Verify the merged `main` commit and its post-merge CI.
5. Confirm that `v0.4.2` does not exist locally or remotely.
6. Create annotated tag `v0.4.2` on the new version-bump merge commit with tag
   message `Wooptima DB Tuner v0.4.2`, then push that exact tag.
7. Require the tag-triggered release workflow to pass its quality,
   integration, artifact-version, runtime-boundary, checksum, attestation, and
   publication steps.
8. Verify the GitHub release and its `dbtune`, checksum, attestation bundle,
   and installer assets.

The tag must not point directly to `34d9db6`, and an existing or failed tag
must never be force-moved.

## Release Note

Draft concise release note:

> Wooptima DB Tuner v0.4.2 strengthens fail-closed database tuning safety.
> It adds authenticated audit/apply provenance, live loaded-default landmine
> checks, exact grant and counter evidence, hardened lock and publication
> boundaries, and a guarded fast local verification gate. MariaDB 10.6 and
> 11.4 remain the tested integration targets.

The tag workflow may append automatically generated commit and contributor
notes. The concise note above remains the release summary.

## Error Handling

- If any local, PR, post-merge, or tag workflow gate fails, stop publication
  and diagnose the failure; do not skip or retry by moving the tag.
- If the built executable does not print `dbtune 0.4.2`, do not create the tag.
- If the remote tag appears concurrently, stop and inspect it rather than
  overwriting it.
- If release asset attestation or policy verification fails, leave the failed
  workflow evidence intact and do not represent the release as published.

## Success Criteria

- `main` contains the version-bump merge and has green post-merge CI.
- `dist/dbtune version` prints exactly `dbtune 0.4.2` from a production build.
- Annotated tag `v0.4.2` resolves to the version-bump merge commit.
- The release workflow succeeds without force-moving or recreating the tag.
- The GitHub release exposes all expected verified assets.
- The audit-only pilot remains documented as owner-waived, not PASS.
