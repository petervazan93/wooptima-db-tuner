# dbtune v0.4.0 English base, localization, and homepage design

Date: 2026-08-03
Status: approved

## Goal

Make English the default language for the complete dbtune project while
retaining Slovak as an explicitly selected interface language. Redesign the
GitHub README as a product-first homepage for RunCloud operators managing
WordPress and WooCommerce workloads.

This is a separate `v0.4.0` feature release built on the published `v0.3.0`
release. It does not change MariaDB tuning formulas or weaken any audit,
apply, verification, provenance, or rollback guard.

## Language contract

The public interface variable is:

```text
DBTUNE_UI_LANG=en|sk
```

The default is `en`. The only supported values are `en` and `sk`. An empty
value is treated as the default. Any other non-empty value is rejected with
exit status 64 before command dispatch.

The first implementation does not infer the interface language from `LANG`,
`LC_MESSAGES`, or another operating-system locale. This keeps unattended
execution, generated artifacts, and tests deterministic. A global `--lang`
option is outside the v0.4.0 scope; the environment variable works for both
interactive and systemd execution without changing the existing CLI grammar.

Examples:

```bash
sudo dbtune audit
sudo DBTUNE_UI_LANG=sk dbtune audit
```

## Localization architecture

The assembled Bash artifact gains an early `lib/05-i18n.sh` module. It
provides a static, trusted catalog and the following interface:

```text
dbtune_i18n_init
dbtune_i18n_set LANGUAGE
dbtune_msg MESSAGE_ID
dbtune_printf MESSAGE_ID [ARG...]
dbtune_eprintf MESSAGE_ID [ARG...]
```

Message identifiers and the default catalog are English-based. Slovak text
exists only in the trusted static catalog and test expectations. Translation
formats are never loaded from writable files, sourced from the environment,
or evaluated. Dynamic values remain separate arguments to trusted format
strings. Existing output redaction and Markdown escaping continue to apply
after localization.

`install.sh` remains POSIX `sh` and implements the same public language
contract with a small static POSIX-compatible message selector. It does not
gain a Bash dependency or load the runtime catalog externally.

## Localized interfaces

The selected language controls:

- CLI help, usage, progress, warnings, and errors;
- audit terminal summaries;
- collect, analyze, report, and propose messages;
- Markdown report headings, labels, reasons, and action warnings;
- generated CNF comments;
- apply, verify, rollback, recovery, and status explanations;
- `ROLLBACK.txt` and apply reports;
- installer help, progress, and errors;
- exact interactive safety confirmation phrases.

Build tooling, public documentation, source comments, internal identifiers,
and test descriptions use English as their single source language.

## Stable machine contracts

The following values are never localized:

- CLI command and option names;
- JSON and TSV keys and headers;
- schema versions;
- state, severity, verdict, status, and capability enums;
- event names and event field names;
- manifest keys, hashes, and fingerprints;
- MariaDB variable names;
- exit statuses;
- machine-readable booleans, which use `true` and `false`.

Human-readable stderr and Markdown may vary by language. Machine consumers
must continue to use stable keys, enums, IDs, and exit statuses rather than
parse translated prose.

## Analysis and report schema

The existing `analysis.tsv` stores Slovak prose in the hash-bound `reason_sk`
column. Version 0.4.0 replaces that column with a stable `reason_id` while
retaining the eight-column structure:

```text
rule_id
scope
severity
verdict
proposed_key
proposed_value
evidence
reason_id
```

Rule-specific dynamic values remain in the existing evidence field. The
presentation layer resolves `reason_id` through the selected catalog. This
makes `analysis.tsv`, `analysis_hash`, `analysis_fingerprint`, and proposal
record semantics independent of the display language.

The flat JSON report advances from `fleet-v2` to `fleet-v3`. It publishes the
selected language, stable reason and warning IDs, and localized display text.
Machine consumers use the IDs. A report may differ by language, but its input
provenance and proposal key/value semantics do not.

Localized CNF comments may make the final proposal file hash language-specific.
The proposal remains safe because its manifest binds the exact reviewed file,
while the canonical proposal records hash remains language-neutral.

## Upgrade behavior

Existing persisted lifecycle data is a concrete compatibility boundary.
Version 0.4.0 does not silently reinterpret, translate, or rehash a v0.3.0
analysis. When report, propose, or apply encounters the old `reason_sk` header,
it fails closed with an explicit instruction to run a new audit and measurement
cycle under v0.4.0.

Apply history and rollback data remain available. Starting a new audit follows
the existing lifecycle behavior and does not delete apply recovery history.

## Collector language persistence

`collect start` records the validated selected language as `ui_lang` in the
root-owned `collect.tsv`. A systemd `_tick` restores that value before it emits
user-visible diagnostics or triggers automatic analyze and report operations.
This ensures the final unattended report uses the language selected when the
collection began without trusting the service manager's ambient locale.

## Safety confirmations

The exact force confirmation phrases are:

```text
en: APPLY WITHOUT MEASUREMENTS
sk: APLIKUJ BEZ MERANIA
```

The exact backup confirmation phrases are:

```text
en: I CONFIRM A RESTORABLE BACKUP
sk: POTVRDZUJEM OBNOVITELNU ZALOHU
```

The process selects each phrase once from the trusted catalog, displays that
same value, and performs an exact byte comparison. It does not use regular
expressions, case folding, or environment-provided phrase text. Events record
stable confirmation IDs and `ui_lang`, never a translated phrase as a state
value.

## English source base

The following public and developer-facing files become English:

- `README.md`;
- `SECURITY.md`;
- `docs/RUNBOOK.md`;
- `docs/PILOT-AUDIT.md`;
- `mariadb-runcloud-preset.md`;
- `PLAN.md`;
- source comments, test descriptions, build messages, and integration harness
  messages.

Historical design and implementation documents that are already English need
no translation. Slovak documentation variants are outside v0.4.0 scope; the
optional Slovak contract applies to the executable interface.

## GitHub homepage

`README.md` becomes a concise product-first homepage modeled on the information
hierarchy of successful open-source projects without copying their content or
marketing scale. Its order is:

1. centered name, value proposition, navigation, and factual badges;
2. a terminal-style image generated from authentic sanitized English output;
3. product overview and operator benefits;
4. lifecycle explanation;
5. read-only quickstart;
6. safety model;
7. supported environment matrix;
8. pinned, attestable installation;
9. CLI and documentation links;
10. development and security information.

The primary tagline is:

```text
Evidence-based MariaDB tuning for RunCloud-hosted WordPress and WooCommerce.
```

The screenshot contains no hostname, IP address, webroot, database name,
credential, or production evidence. The README does not display a license badge
unless the repository gains a license file. It does not recommend piping a
remote installer into a privileged shell.

## Verification

Unit coverage must include implicit English, explicit English, explicit Slovak,
invalid language rejection, catalog completeness, both safety phrase pairs,
old analysis schema rejection, and language-neutral machine contracts.

Integration runs the full MariaDB 10.6 and 11.4 lifecycle in English and
Slovak. It verifies the report language and confirms that proposal keys and
values remain equivalent.

The release gate remains `make check`, all Bats tests, required Docker
integration, artifact version verification, checksum verification, and GitHub
artifact attestation. The `v0.4.0` tag is created only after the implementation
branch is reviewed, merged, and green on `main`.

## Success criteria

- With no language setting, every supported user-visible interface is English.
- `DBTUNE_UI_LANG=sk` selects the Slovak executable interface.
- Invalid language values fail before command dispatch.
- Machine keys, enums, analysis data, and canonical proposal records are
  language-neutral.
- Safety prompts accept only the exact phrase for the active language.
- Automatic reports preserve the language selected by `collect start`.
- Public documentation and source comments use English as the base language.
- The GitHub README communicates the product value, safety model, quickstart,
  support matrix, and verifiable installation path before internal details.
- Static, unit, English integration, Slovak integration, release, checksum, and
  attestation gates pass.
