# v0.4.2 integrated safety and alignment design

Date: 2026-08-06
Status: approved

## Goal

Ship one coherent safety release in which audit evidence, executable rules,
human reports, generated MariaDB configuration, apply validation, and the tuning
methodology describe the same contract.

The release integrates the completed P0 privileged-boundary work, finishes the
approved P1 fail-closed package, adds full managed desired-state proposals,
executes the P2 audit-accuracy work, and removes current methodology drift that
would otherwise misstate implemented behavior.

## Safety principles

The release preserves the P1 principles and adds one desired-state invariant:

1. Unknown is not zero, absent, safe, disabled, or permission to remove a
   previously managed setting.
2. Validation succeeds only on complete exact input, never on an accepted
   subset.
3. The bytes validated are the bytes recorded and published.
4. New forward-safety gates may block apply but never rollback or recovery.
5. A generated managed CNF is the complete desired state of that managed file,
   not the latest diff against live MariaDB values.

`--force` retains the P1 boundary. It may bypass measurement and provenance
requirements and the local time window. It may not bypass strict CNF grammar,
live-variable validation, loaded-default checks, backup, target, topology,
Galera, mydumper, daemon validation, rollback, or recovery guards.

## Artifact architecture

### Analysis remains a diff contract

`analysis.tsv` keeps its existing exact eight-column schema:

```text
rule_id scope severity verdict proposed_key proposed_value evidence reason_id
```

It remains the operator-facing explanation of differences, findings, and
actions. P1 tri-state semantics remain unchanged: only explicit changing
verdicts may carry proposal key/value fields. `UNKNOWN`, `REVIEW`, `KEEP`, `OK`,
`NO-SHRINK`, `UNSUPPORTED`, and other non-changing verdicts must not acquire
proposal fields merely to support desired-state rendering.

This preserves the existing report and additive `fleet-v3` change-list contract.

### Desired state is a separate rule output

Analyze also produces `desired-state.tsv`. It is not inferred from only the
changing rows in `analysis.tsv`; the rules engine emits it while it still knows
the target, current evidence, version policy, and reason for every managed key.

Each desired-state record has this exact eight-column schema:

```text
rule_id key disposition value basis observed_value evidence reason_id
```

The allowed dispositions are:

| Disposition | Value | Meaning |
| --- | --- | --- |
| `manage` | Required | The complete managed CNF must contain this key/value. |
| `retire` | Empty | The key is intentionally no longer valid for this server family and must be absent from the new managed CNF. |
| `unresolved` | Empty | Evidence is insufficient to choose or retain a safe managed value. |

The allowed basis values are `computed`, `pinned`, `current`, `version`, and
`evidence`. They explain why the disposition exists but do not weaken
validation.
`observed_value` contains the exact validated audit value used by the decision,
or is empty when no valid current value exists. It is machine input for the
final stale-evidence check, never a value recovered by parsing prose evidence.

Field relationships are exact:

- `manage` requires basis `computed`, `pinned`, or `current`, plus non-empty
  valid `value` and `observed_value`;
- `manage` with basis `current` requires `value` and `observed_value` to be
  semantically equal under the key's type schema;
- `retire` requires basis `version` and empty `value` and `observed_value`;
- `unresolved` requires basis `evidence` and empty `value` and
  `observed_value`.

Keys are canonical lowercase names with hyphens normalized to underscores.
Every key appears at most once. Values pass the same sensitive-key and value
grammar used by the strict CNF parser. `rule_id`, `key`, `disposition`, `basis`,
and `reason_id` are non-empty; evidence may be empty. Unknown disposition,
basis, duplicate, one-sided value, malformed field count, control character,
unsafe key/value, or a rule ID that does not own the key in the catalog
invalidates the entire artifact.

The rule engine emits desired records independently of diff verdicts:

- a computed or pinned target emits `manage` even when live MariaDB already has
  the equivalent value;
- a deliberate keep or review with complete valid current evidence emits
  `manage` using that current value and basis `current`;
- a version-removed setting emits `retire`;
- missing, malformed, degraded, or insufficient evidence emits `unresolved` for
  each affected managed key.

The disposition matrix is exhaustive:

| Rule outcome | Catalog-key decision |
| --- | --- |
| Known computed or pinned target, changed or equivalent | `manage` with the target and validated observed value. |
| `KEEP`, `REVIEW`, or `NO-SHRINK` with valid current evidence | `manage` with current value and basis `current`. |
| `MEMORY-GUARD` with valid current evidence | `manage` with current value and basis `current`; otherwise `unresolved`. |
| Missing, malformed, degraded, or insufficient evidence | `unresolved`. |
| Version-removed or explicitly unsupported option on a supported server family | `retire` with basis `version`. |
| Unsupported MariaDB family | No proposal is permitted; the server-family gate fails before compilation. |

An aggregate `KEEP`, such as query-cache retention, emits one `manage` record
for every catalog key it owns. Findings and actions that own no managed setting
emit no desired-state rows.

Aggregate analysis findings may still represent several desired-state records.
For example, unknown storage classification remains one operator-facing
`R-IO-CAP UNKNOWN` row but emits an `unresolved` desired record for each affected
I/O setting.

### Managed setting catalog

One executable managed-setting catalog defines the keys owned by the generated
CNF and their responsible rule IDs. Desired-state validation requires exactly
one decision for every catalog key applicable to the detected MariaDB family.
The catalog also retains retirement tombstones for every key emitted by a prior
supported release, including v0.4.1, so an old managed target can always be
classified as `manage` or `retire` rather than becoming permanent catalog drift.
It additionally contains retirement-only tombstones for the P1 critical
landmine options that `dbtune` must be able to remove from an existing managed
target. These tombstones are not active proposal-capable settings, are not
counted among the published 29 keys, and can never produce `manage` decisions.

The catalog is used by rules, proposal generation, tests, and methodology
contract review. Consumers may not maintain private subsets. Version-gated keys
remain in the catalog with explicit `retire` decisions when they are no longer
valid.

The MariaDB evidence schema remains the authority for validators and canonical
types. The managed-setting catalog defines ownership; it does not duplicate
value validation rules.

### Analyze publication and provenance

Analyze stages `analysis.tsv`, `desired-state.tsv`, and their manifest inputs in
private files. It validates all staged files before publication, then publishes
the analysis and desired state before publishing the manifest as the logical
commit marker. The manifest is the only commit marker: a crash between data-file
publication and manifest publication leaves an uncommitted, fail-closed set that
the next command rejects and `analyze` may regenerate. It does not claim a
multi-file atomic rename or accept files against an older manifest.

The analysis manifest moves from the existing P1 schema 2 to schema 3. It has
these exact static keys plus the existing exact dynamic selected-row sequence:

```text
schema
run_id
audit_hash
samples_hash
dbsize_input
dbsize_hash
dbsize_selected_hash
dbsize_selected_rows
analysis_hash
analysis_fingerprint
desired_state_hash
desired_state_records_hash
desired_state_count
```

The dynamic keys are exactly `dbsize_selected_row.000001` through the declared
`dbsize_selected_rows` count, with no gaps, duplicates, or additional keys.
`desired-state.tsv` has one literal eight-column header followed by data rows
sorted in `LC_ALL=C` canonical-key order. `desired_state_hash` hashes the whole
file. `desired_state_records_hash` hashes the newline-terminated sorted data rows
without the header, and `desired_state_count` counts those data rows.

Exact-key, exact-count, hash-shape, regular-file, ownership, and mode validation
follow the P1 manifest contract. Existing schema 1 and P1 schema 2 analysis
manifests cannot authorize a v0.4.2 proposal.

## Desired-state compilation

### Previous managed target

`propose` copies the current managed target when it exists to one private,
mode-0400 snapshot before parsing or hashing it. Strict parsing, previous-key
classification, and `previous_target_hash` all consume that one snapshot. The
source target is never reread as trusted input during compilation. A target
change after snapshot creation is safe because normal apply must still match the
snapshot hash and topology immediately before mutation.

That snapshot is the authoritative set of keys currently owned by `dbtune`;
values from other MariaDB option files are not copied into the managed target
merely because they are visible at runtime.

An absent target means the previous managed set is empty. An unreadable,
untrusted, malformed, or duplicate-containing existing target blocks proposal
instead of being treated as absent.

### Compilation rules

For every catalog key:

- `manage` includes the desired key/value in the full candidate;
- `retire` excludes the key and records an intentional retirement;
- `unresolved` excludes a never-managed key but blocks proposal if the key is
  present in the previous managed target;
- a previous managed key with no applicable catalog decision blocks proposal;
- a key in the previous managed target but outside the executable ownership
  catalog blocks proposal as catalog drift.

This rule permits partial ownership of MariaDB configuration while preventing
silent loss of a setting already owned by `dbtune`. It also permits a first run
to leave an evidence-dependent key unmanaged without blocking unrelated safe
settings.

Every `manage` value is checked against the validated current audit evidence and
its type schema. A basis of `current` requires exact valid current evidence; it
cannot be synthesized from `unknown`, `unresolved`, a missing row, or a default.

Compilation must produce at least one `manage` assignment. If all keys are
retired or unresolved, v0.4.2 blocks proposal with an explicit manual-remediation
diagnostic rather than weakening the strict non-empty CNF grammar. Automatic
managed-file deletion is outside this release.

### Semantic equality

One shared type-aware comparison layer decides whether current and desired
values are equivalent. It covers at least:

- booleans such as `ON`, `OFF`, `1`, and `0`;
- byte sizes such as `67108864` and `64M`;
- canonical unsigned integers;
- case-insensitive enums where the MariaDB evidence schema permits them;
- exact strings and paths where normalization would be unsafe.

Equivalent values produce a non-changing analysis verdict while still emitting
a `manage` desired record. Type-invalid values remain unknown and never compare
equal through shell, Bash arithmetic, or AWK numeric coercion.

Normal apply queries the exact live key set represented by `manage` records and
semantically compares every live value with that record's `observed_value`.
Missing, extra, duplicate, malformed, or changed live values require a fresh
audit/analyze/propose cycle. This includes basis `current`, preventing stale
audit evidence from pinning and overwriting a newer runtime value.

## Proposal and report behavior

`proposed-99-zz-tuning.cnf` is rendered from compiled desired state, not from
`DBTUNE_PROPOSAL_LINES` or another change-only array. It contains exactly one
`[mysqld]` section and the complete sorted managed assignment set. Stable key
ordering makes repeated proposals byte-stable except for deliberately variable
header metadata.

The human and JSON reports continue to emphasize actual changes and diagnostics.
They add desired-state metadata and blockers, not a second misleading change
list. The additive `fleet-v3` fields include the desired-state count and hash;
existing proposal entries continue to represent changes.

Proposal publication stages and validates the complete CNF and schema-2
manifest before replacing either previous artifact. It publishes the proposal
first and the manifest last as the commit marker. A crash between them produces
an uncommitted mismatch that apply rejects and `propose` may regenerate. The
proposal manifest exact
schema is:

```text
schema
run_id
audit_hash
samples_hash
analysis_hash
analysis_fingerprint
desired_state_hash
desired_state_records_hash
desired_state_count
previous_target_topology
previous_target_hash
proposal_hash
proposal_count
proposal_records_hash
```

`previous_target_topology` is exactly `regular` or `absent`.
`previous_target_hash` is a SHA-256 for `regular` or the exact token `absent` for
`absent`; all other combinations are invalid.
`proposal_count` and `proposal_records_hash` describe all assignments in the full
candidate, not only changed settings. A zero-assignment candidate is invalid for
apply and is reported as having no safely managed target.

The lifecycle state changes to `proposed` only after the schema-2 manifest is
durably published. If a crash leaves a valid committed proposal while state is
still `analyzed`, a subsequent `propose` validates and republishes it
idempotently before transitioning. If state says `proposed` but the commit
marker or any bound artifact is invalid, apply fails closed and `propose` must
regenerate the set.

## Apply, rollback, and migration

Normal apply requires a schema-3 analysis manifest, schema-2 proposal manifest,
the bound desired-state artifact, the strict proposal snapshot, and every P1
preflight.
It independently verifies that the canonical proposal records equal the
compiled `manage` records, that every live managed value still equals its bound
`observed_value`, and that the current managed target hash and topology still
equal the proposal-time target snapshot immediately before the durable mutation
boundary.

This target-hash check prevents an operator or concurrent run from replacing the
managed file after proposal generation without a fresh cycle.

The full candidate then replaces the managed target atomically under the P0/P1
publication contract. The new apply-history schema records desired-state hashes,
previous target hash, full proposal hashes and count, fresh loaded-defaults
fingerprint, and force flag.

### Controlled critical-option retirement

The normal P1 rule remains that a failed scan or loaded critical option blocks
before mutation. A narrow normal-apply remediation path is required when this
release must remove a critical option from the managed target itself.

The pre-mutation scan may enter controlled retirement only when all of these are
true:

- apply is normal, not forced;
- every loaded critical option has an exact schema-3 `retire` decision;
- every such option is present in the bound previous-target snapshot and absent
  from the full candidate;
- the candidate introduces no critical option and all other P1 gates pass;
- the set contains no loaded critical option without a retirement decision.

Before any history or intent creation, apply validates the exact candidate with
the daemon in the P0 split-ownership temporary workspace using an isolated
defaults input that does not reload the old managed target. This is a
pre-mutation candidate validation, not the validation of the still-installed
configuration.

After history and intent are durable, apply publishes the candidate and
immediately repeats the trusted loaded-defaults scan before configuration
revalidation, state transition, or restart instructions. It then repeats daemon
validation against the complete installed hierarchy. A failed scan, remaining
critical option, or failed repeated daemon validation triggers the existing
automatic restore of the prior target and returns failure. Because
`--print-defaults` does not prove file origin, this post-publication scan is
mandatory even when the old managed target contained the option. Force never
receives this exception.

This is the only v0.4.2 path that may cross the durable boundary after a
pre-mutation critical finding. It removes an already loaded invalid option; it
cannot add, ignore, or retain one.

The migration is intentionally fail-closed:

- v0.4.1 proposal manifests and pre-schema-3 analysis manifests cannot
  authorize normal v0.4.2 apply;
- active v0.4.1 collection files follow the already approved P1 sample-schema
  boundary;
- the operator must run a fresh audit, collection, analyze, report, and propose
  cycle;
- existing apply history remains readable and rollbackable;
- rollback and crash recovery do not require schema-3 desired-state artifacts,
  current audit evidence, SQL, or a loaded-default scan.

Forced apply treats its strict source CNF as an overlay, never as replacement
proof. It snapshots and strictly parses both the source CNF and current managed
target, overlays source assignments by canonical key, renders a private complete
candidate, then strictly parses and validates that candidate. The candidate
bytes, not the overlay source, are the bytes recorded and atomically published;
history binds source, previous-target, candidate, and canonical-record hashes.

Every source and previous-target key must exist in the executable ownership
catalog. Force cannot introduce an arbitrary safe-syntax MariaDB option outside
that catalog. This guarantees that the next normal cycle can classify every key
instead of failing on ownership drift created by the tool itself.

This makes a legacy v0.4.1 change-only file non-destructive under `--force`:
settings already present in the managed target are retained. Force cannot retire
or delete a previously managed key. Retirement requires a normal schema-3
analysis/schema-2 proposal pair or explicit out-of-band operator remediation.
Force still cannot weaken target, live-value, landmine, backup, or publication
checks.

## Audit accuracy integration

### Listener scope

P2 adds the exact language-neutral enum:

```text
security.port_3306=public|network|local|not_listening|unknown
```

Precedence is `public > network > local > not_listening`. Wildcard endpoints are
public, concrete non-loopback addresses are network, `127.0.0.0/8` and `::1` are
local, and command failure or unclassifiable evidence is unknown.

R-SEC applies this exact order:

```text
incomplete grant evidence or listener=unknown -> UNKNOWN
listener=public or remote_grant_count>0        -> high EXPOSED
listener=network                               -> medium NETWORK-BOUND
listener=local or not_listening                -> info OK
```

Known remote grants do not override an unknown listener into a definitive
exposure result because the complete security decision requires both facts.

### WordPress autoload

Aggregate audit SQL, top-option SQL, generated read-only diagnostics,
integration fixtures, documentation, and current diagrams use the same exact
WordPress 6.6+ autoload-on set:

```sql
('yes','on','auto-on','auto')
```

`no`, `off`, and `auto-off` remain excluded. Thresholds and recommendation-only
behavior do not change.

### HPOS evidence absence

Missing HPOS option evidence or unavailable HPOS row evidence does not become a
definitive disabled or zero-row conclusion. The exact evidence behavior is:

| Condition | Evidence and finding behavior |
| --- | --- |
| Successful option query with no matching row | Option status is `unknown_absent`; no migration or sync finding. |
| Successful table-existence query with no HPOS table | Table status is `absent`; row count is unavailable, not zero. |
| Explicit disabled option, known legacy order count, and absent HPOS table | The existing recommendation-only migration finding may be emitted. |
| SQL permission, connection, or command failure | Application evidence is partial with `query_failed`; no dependent finding. A globally required SQL failure retains status 69. |
| Malformed or partial SQL output | Data error 65 for that evidence path; it is never treated as an empty result. |

Optional application diagnostics may leave their application section partial
under the existing audit contract, but they must distinguish command failure
from a successful empty result.

This release does not compare or reconcile row counts between legacy and HPOS
storage and does not perform migration.

## Methodology contract

Current documentation is reorganized into three visibly distinct layers:

1. **Automated contract:** behavior performed by audit, collect, analyze,
   report, propose, apply, verify, rollback, or recovery.
2. **Collected diagnostics:** read-only evidence and recommendations that do not
   become MariaDB configuration assignments.
3. **Manual advisory workflow:** operator procedures and external-system tuning
   that `dbtune` does not execute or verify.

Executable rules, schemas, catalogs, and tests are normative when prose and code
disagree. The current documentation must nevertheless match them before release.

The alignment review covers at least:

- all managed proposal keys, version gates, formulas, and no-shrink behavior;
- the distinction between a change-only report and a full managed candidate;
- query-cache denominator and degraded-sample behavior;
- `skip_name_resolve` grant-evidence gating;
- listener enum and exposure severity;
- four-value autoload-on filtering;
- HPOS unknown-evidence behavior and recommendation-only scope;
- Redis policy versus excluded memory sizing;
- backup evidence versus excluded provider/cadence automation;
- loaded-default landmine detection and live apply recheck;
- exact `--force`, restart, rollback, and recovery boundaries.

Claims that are not executable are labeled manual. Unsupported numeric floors or
defaults are removed instead of being presented as hidden tool behavior.
Historical dated specifications remain unchanged.

## Error behavior

Malformed desired state, missing decisions, unsafe values, unresolved previously
managed keys, manifest mismatch, stale target hash, or v0.4.1 proposal provenance
returns the existing data/safety status `65` before durable mutation.

Failure to execute a required command or contact required SQL follows the
existing infrastructure status `69`. Partial or malformed output remains `65`.

Diagnostics identify the blocking rule/key and the required fresh-cycle or
evidence action without logging credentials, raw grants, or unnecessary values.
Handled proposal failure restores or retains the prior committed pair. Process
death during multi-file publication may leave uncommitted data, but never a new
matching commit marker; consumers reject the mismatch and `propose` regenerates
it. Apply failure before the durable boundary leaves history, intent, state,
current pointer, target, and service unchanged. Controlled-retirement failure
after that boundary uses the existing automatic restore path.

## Compatibility

The public CLI, English/Slovak selector, additive `fleet-v3` contract, normal
RunCloud manual-restart workflow, and existing rollback history remain supported.

Intentional boundaries are:

- analysis manifest schemas 1 and 2 and proposal manifest schema 1 require a
  fresh normal workflow;
- v0.4.1 active 20-column samples require the P1 fresh collection cycle;
- the listener enum gains additive `network`;
- schema-2 proposal count means complete managed assignments rather than only
  changed assignments;
- new histories carry desired-state provenance while old histories remain
  rollbackable.

## Testing strategy

### Pilot contract

The release uses two distinct pilot checkpoints and never describes collection
as read-only:

1. The **audit-only pilot** follows `docs/PILOT-AUDIT.md`. It runs only `audit
   --json`, validates the new landmine, grants, listener, and section-status
   evidence, preserves existing history, and performs no collection or lifecycle
   mutation.
2. The **no-apply measurement rehearsal** starts from a fresh successful audit
   in a dedicated state directory, runs one complete collection window through
   automatic analyze and report, and verifies cleanup/restoration. It may make
   the documented temporary slow-log and systemd timer/service changes required
   by collection, so it requires an approved non-critical host and explicit
   operator consent. It must not run `propose`, `apply`, `--restart`, or
   `rollback`.

The two results are recorded separately. Passing the audit-only pilot does not
claim that collection was rehearsed, and passing the measurement rehearsal does
not authorize apply.

Every behavior change follows a red-green cycle. In addition to the complete P1
and P2 test matrices, required desired-state coverage includes:

- a second proposal after a prior apply preserves every still-managed setting
  while changing only one report entry;
- an all-equivalent run emits no changes but reproduces the complete managed
  candidate;
- boolean, size, integer, enum, string, and path semantic comparisons;
- unresolved never-managed keys remain outside the candidate without blocking
  unrelated safe keys;
- unresolved previously managed keys block proposal and preserve old artifacts;
- explicit family retirement removes a previously managed key;
- controlled retirement allows only the exact critical set owned by the old
  target, daemon-validates the isolated candidate before history, rescans and
  revalidates after publication, and restores on any failure or leftover;
- force rejects retirement and merges a legacy change-only source over the
  previous managed snapshot without dropping prior assignments;
- force rejects source or previous-target keys outside the ownership catalog;
- a valid v0.4.1 managed target maps every historical key to an active catalog
  entry or retirement tombstone;
- old-history rollback followed by a fresh schema-3 analysis/schema-2 proposal
  cycle and apply succeeds;
- missing, duplicate, unknown, malformed, unsafe, or conflicting desired-state
  rows fail closed;
- valid legacy analysis schema 2, proposal schema 1, and malformed current
  schema-3 analysis/schema-2 proposal manifests are rejected for normal apply;
- desired-state, target, proposal, and canonical-record hash tampering is caught
  at every validation and publication boundary;
- target replacement between proposal snapshot, parse, and hash cannot change
  the compiled previous-key set and causes apply to fail stale;
- replacement of the managed target after propose blocks normal apply;
- a live value changed after analyze/propose fails the observed-value preflight;
- crashes before and after each analysis/proposal data-file, commit-marker, and
  lifecycle-state publication leave either a valid committed set or a rejected,
  regenerable set;
- an all-retired or all-unresolved zero-assignment target is blocked with the
  manual-remediation diagnostic;
- normal and forced apply obey the final P1 preflight matrix;
- rollback and recovery work with old history and missing desired-state files;
- HPOS missing option, missing table, SQL failure, and malformed-output cases
  follow their distinct evidence/error contracts;
- MariaDB 10.6 and 11.4 integration validates full candidate persistence across
  consecutive cycles.

Documentation verification checks current README, runbook, security, plan,
methodology, EN/SK catalogs, and both current SVGs where P2 changes visible text.

## Completion gate

The release is complete only when:

- P0 remains present and its privileged-boundary tests pass;
- every P1 completion condition and audit-only pilot checkpoint passes;
- a generated CNF is proven to be the complete managed desired state;
- no previous managed key can disappear through an unknown or absent decision;
- legacy analysis schema 1/2 and proposal schema 1 fail normal use with a clear
  fresh-cycle diagnostic;
- old history rollback and crash recovery remain operational;
- P2 listener and autoload contracts pass unit and real integration tests;
- methodology claims are classified and match executable behavior;
- generated `dist/` files are absent from the commit diff;
- `make build`, `make check`, `make test`, required MariaDB integration, catalog
  checks, XML validation, visual SVG inspection, and `git diff --check` pass;
- the final audit-only pilot and separate no-apply measurement rehearsal both
  pass under their distinct contracts.

## Expected result

`v0.4.2` cannot turn incomplete evidence into a tuning decision and cannot turn
a change-only diff into a destructive replacement configuration. Reports remain
focused on operator-visible changes, while proposal and apply operate on one
complete, exact, provenance-bound managed state. The executable behavior and
current methodology describe the same safety and tuning boundaries.
