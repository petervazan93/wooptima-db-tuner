# dbtune v0.3.0 release and documentation design

Date: 2026-08-02
Status: approved

## Goal

Publish the current hardened `main` as `v0.3.0` and make `README.md` and
`SECURITY.md` describe the behavior of the published release rather than a
newer, unreleased worktree. Enable a real private vulnerability reporting
channel through GitHub.

## Scope

The change includes:

- changing `DBTUNE_ARTIFACT_VERSION` from `0.2.0` to `0.3.0`;
- updating pinned installation examples to `v0.3.0`;
- documenting release selection, trust policy, dependencies, supported and
  tested platforms, audit exit statuses, and attestation subjects precisely;
- enabling GitHub Private Vulnerability Reporting;
- verifying, tagging, and publishing `v0.3.0` through the existing release
  workflow.

The change does not add runtime features or alter tuning rules. Release
`v0.2.0` remains available as historical software, but current documentation
will no longer present it as the recommended hardened release.

## Version and release identity

`lib/00-header.sh` remains the single source of artifact version truth. It
will declare `0.3.0`. The release workflow must continue to prove that
`dist/dbtune version` equals the pushed tag before creating a release.

The release is created only from a clean, pushed `main` commit whose CI run is
green. An annotated `v0.3.0` tag points to that exact commit. The tag is never
force-moved. A transient workflow failure may be rerun against the same tag;
a code defect discovered after tagging requires a new patch release rather
than rewriting `v0.3.0`.

## README changes

The installation section will recommend a pinned `v0.3.0` download. It will
explain that `latest` is a moving selector: the installer first resolves it
through trusted GitHub release metadata to a concrete semantic-version tag,
then downloads and verifies artifacts against that exact source ref. Version
values with and without the leading `v` are accepted, while pinned `vX.Y.Z`
is the recommended production form.

`DBTUNE_REPOSITORY` remains unsupported. `DBTUNE_DOWNLOAD_BASE` is documented
as an internal test or controlled mirror transport only. It does not change
the upstream repository, owner, signer workflow, or source-ref trust policy.
The `file://` form is not a production installation path.

The README will add a support matrix:

| Category | Contract |
| --- | --- |
| Accepted MariaDB families | 10.6, 10.11, and 11.x |
| Integration-tested MariaDB | 10.6 and 11.4 |
| CI operating system | Ubuntu 24.04 |
| Intended deployment | Linux RunCloud hosts with systemd |
| Not implied | Every Ubuntu release or every 11.x minor is integration-tested |

Dependencies will be grouped by purpose:

- installer: POSIX `sh`, Linux, `curl`, GitHub CLI `gh`, Bash 4+, `install`,
  `stat`, SHA-256 tooling, and `sudo` when the destination needs elevation;
- core runtime: Bash 4+, standard GNU/Linux tools, and `flock`;
- database operations: MariaDB/MySQL client plus supported root socket or
  defaults-file authentication;
- lifecycle apply, rollback, and recovery: Python 3 with `dir_fd` and Linux
  `renameat2`, systemd tooling, and the MariaDB daemon validation command;
- authoritative hardware/security audit: `findmnt`, `lsblk`, `ss`, `free`,
  and `pgrep` where their evidence domains are required;
- WordPress actions: WP-CLI is optional and actions remain non-executable when
  a verified non-root owner or canonical webroot is unavailable;
- development: Bats, ShellCheck, Docker, and Docker Compose.

Audit result statuses remain `PASS`, `FINDINGS`, `UNKNOWN`, and `ERROR`.
Classification exits are documented separately as `0`, `0`, `2`, and `1`.
Usage, validation, unavailable dependency, and other technical failures may
use the established `64+` exit-code range and must not be interpreted as an
audit classification.

## SECURITY changes

The installation description will say that GitHub Releases is the default
transport, not the only possible transport. It will explicitly state that a
transport override cannot alter the immutable upstream attestation policy.

The release attestation description will state that one SLSA provenance
statement contains three subjects:

- `dist/dbtune`;
- `dist/dbtune.sha256`;
- `install.sh`.

`dbtune-attestation.jsonl` is the offline bundle, not an attested subject.
The checksum file records the digest of `dbtune`. The manual preflight verifies
the `install.sh` subject. The installer checks the checksum and verifies the
`dbtune` subject against repository, owner, workflow, exact tag, and
GitHub-hosted-runner policy.

GitHub Private Vulnerability Reporting will be enabled with the repository API.
`SECURITY.md` will link reporters to the repository Security advisory form and
will retain the warning not to place credentials or raw production evidence in
public issues. No unsupported claim about private messages through a GitHub
profile remains.

## Verification flow

Before the release-preparation commit:

1. Run `make check`.
2. Run `make test` and require all tests to pass.
3. Run integration in required mode on MariaDB 10.6 and 11.4.
4. Build the artifact and require `dist/dbtune version` to print `0.3.0`.
5. Check the full diff and whitespace.

After the release-preparation commit:

1. Push `main` and wait for its CI run to succeed.
2. Enable GitHub Private Vulnerability Reporting and verify it reports
   `enabled: true`.
3. Create and push annotated tag `v0.3.0`.
4. Wait for the release workflow to succeed.
5. Verify that the GitHub release contains `dbtune`, `dbtune.sha256`,
   `install.sh`, and `dbtune-attestation.jsonl`.
6. Verify the downloaded checksum and offline attestation policy.
7. Run an installer smoke test against the real pinned release without
   modifying a privileged system destination.
8. Confirm the local and remote tag resolve to the same commit and the
   worktree remains clean.

## Failure handling

Documentation or version mismatches block the release before tagging. Any
failed static, unit, integration, checksum, attestation, or installer-smoke
gate blocks completion. No failed gate is bypassed and no tag is force-moved.
Private vulnerability reporting must be verified independently of the text in
`SECURITY.md`; documentation alone is not evidence that the channel works.

## Success criteria

- `dbtune version` reports `0.3.0` in source, build output, and release asset.
- README installation commands point to `v0.3.0` and accurately describe its
  behavior and prerequisites.
- SECURITY describes the actual transport and attestation boundaries.
- Private Vulnerability Reporting is enabled.
- Local verification, main CI, release workflow, release asset verification,
  and installer smoke test all pass.
- The published tag and release point to the reviewed release-preparation
  commit without rewriting history.
