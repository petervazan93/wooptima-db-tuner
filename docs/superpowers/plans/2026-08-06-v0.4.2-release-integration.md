# v0.4.2 Release Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Integrate completed P1 safety, full desired-state apply, P2 audit accuracy, HPOS/methodology alignment, versioning, CI, pilots, and publication into one verifiable v0.4.2 release train.

**Architecture:** The release is a strict sequence of independently gated plans rather than parallel feature branches over stale code. The existing design worktree is the integration line because it already contains P1 Tasks 1–5 and the approved v0.4.2 design. Each subsystem passes its own completion gate before the next begins; merge, tag, push, and GitHub release are separate approval-controlled publication steps.

**Tech Stack:** Git worktrees, Bash 4+, Bats, ShellCheck, Docker Compose, MariaDB 10.6/11.4, GitHub Actions, GitHub artifact attestations, xmllint, Markdown/SVG validation.

## Global Constraints

- Use the isolated worktree `.worktrees/v0.4.2-integrated-safety-design`; do not implement in the stale local `main` checkout.
- Preserve untracked files in the main checkout; never stash, delete, overwrite, or stage them without explicit owner approval.
- Treat `origin/main=3d3bcdf6e7337e49ebaf6769c47199da87fff3fe` as the P0 merge baseline.
- Treat P1 tip `ee6c5dc1f5f2c93ec4f7d12b3623abace9b1fb0b` plus design/pilot commits as the current integration ancestry.
- Execute P1 before desired-state, desired-state before P2, and P2 before HPOS/methodology alignment.
- Do not develop P2 in parallel from old `main` or a partially completed P1 branch.
- Do not manually edit or commit generated files under `dist/`.
- Every subsystem must pass focused, full unit, required integration, catalog, and diff gates specified by its own plan.
- The audit-only pilot and no-apply measurement rehearsal are separate checkpoints; collection is never called read-only.
- Do not merge, push, tag, or create a GitHub release without explicit approval at the publication checkpoint.
- Keep all code comments in English.
- Historical dated specifications and plans remain unchanged except the current v0.4.2 documents created for this release.
