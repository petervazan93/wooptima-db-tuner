# v0.4.2 Desired-State and Apply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace change-only MariaDB proposal publication with one exact, provenance-bound full managed state while preserving change-focused reports, fail-closed apply, force safety, and old-history rollback.

**Architecture:** The rules engine emits unchanged eight-column `analysis.tsv` plus a separate exact eight-column `desired-state.tsv`. A family-aware managed-setting catalog and typed MariaDB value API validate that state; schema-3 analysis provenance and schema-2 proposal provenance bind it to a snapshot of the previous managed target. Normal apply verifies observed live values and the target snapshot, while forced apply publishes a catalog-only overlay candidate and controlled retirement uses a normal-only double-scan recovery path.

**Tech Stack:** Bash 4+, AWK, Bats, SHA-256 manifests, MariaDB 10.6/11.4, strict CNF parsing, Python atomic publisher, Docker Compose.

## Global Constraints

- Begin only from a descendant containing completed P1 Tasks 6 and 7, a passing P1 completion gate, and the approved design commit `11aa6de`.
- Preserve the public CLI, English/Slovak selector, eight-column `analysis.tsv`, additive `fleet-v3`, RunCloud manual restart workflow, and old rollback history.
- Keep `DBTUNE_PROPOSAL_LINES` change-only; desired state must use separate records and arrays.
- Analysis manifest schema is exactly 3; proposal manifest schema is exactly 2.
- Unknown is never zero, absent, safe, disabled, or permission to remove a previously managed setting.
- A normal candidate contains every `manage` assignment and silently drops no previous managed key.
- `--force` is a catalog-only overlay over the current managed target and cannot retire or delete keys.
- Controlled critical retirement is normal-only and must restore the old target on post-publication scan or daemon-validation failure.
- Forward safety checks must never be added to rollback or crash recovery.
- Do not manually edit or commit generated files under `dist/`.
- Write each regression test first, confirm the intended failure, implement the smallest change, and rerun focused and relevant full suites.
- Keep all code comments in English.
- Do not modify historical dated specifications or older plans.
