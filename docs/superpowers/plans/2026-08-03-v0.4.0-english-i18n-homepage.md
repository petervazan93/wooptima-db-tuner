# dbtune v0.4.0 English Base, Localization, and Homepage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make English the default project and interface language, add an explicitly selected Slovak executable interface, and replace the README with a product-first GitHub homepage.

**Architecture:** Add a trusted static Bash message catalog selected by `DBTUNE_UI_LANG=en|sk`, then migrate runtime prose to stable message IDs while keeping machine contracts language-neutral. Replace the hash-bound Slovak rule prose with `reason_id`, localize only presentation artifacts, persist collector language for systemd, and update documentation after runtime behavior is stable.

**Tech Stack:** Bash 4+, POSIX sh installer, Bats, ShellCheck, Docker Compose, Markdown, SVG, GitHub Actions.

## Global Constraints

- Build from the published `v0.3.0` commit and release as a separate `v0.4.0` feature release.
- `DBTUNE_UI_LANG` supports exactly `en` and `sk`; empty or unset means `en`; any other non-empty value exits 64 before dispatch.
- Do not infer interface language from `LANG`, `LC_MESSAGES`, or another operating-system locale.
- Do not add a gettext or other runtime dependency, `eval` translation text, or load translations from writable files.
- Keep command names, options, JSON/TSV keys, headers, enums, event fields, manifest fields, hashes, fingerprints, and MariaDB variable names language-neutral.
- Preserve all audit, measurement, backup, apply, validation, provenance, rollback, and recovery guards.
- Use exact safety phrases from the approved design and exact byte comparisons.
- Keep source comments, test descriptions, public documentation, and development output in English; Slovak may appear only in trusted catalogs and Slovak test expectations.
- Do not add a license badge while the repository has no `LICENSE` file.
- Do not recommend piping a remote installer into a privileged shell.
- Use TDD for each runtime change and keep every task independently testable.
