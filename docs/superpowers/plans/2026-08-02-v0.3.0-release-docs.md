# dbtune v0.3.0 Release and Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish the hardened current `main` as `v0.3.0`, make the public documentation match that release, and enable a working private vulnerability reporting channel.

**Architecture:** Keep `lib/00-header.sh` as the single artifact-version source and use the existing tag-triggered release workflow as the only publisher. Documentation changes describe the existing installer, audit, lifecycle, and attestation boundaries without changing runtime behavior. Operational release tasks happen only after local verification and a green CI run on the exact release commit.

**Tech Stack:** Bash 4+, POSIX shell installer, Bats, ShellCheck, Docker Compose, GitHub Actions, GitHub CLI, GitHub artifact attestations.

## Global Constraints

- Artifact version and release tag are exactly `0.3.0` and `v0.3.0`.
- Accepted MariaDB families are 10.6, 10.11, and 11.x.
- Integration-tested MariaDB versions are 10.6 and 11.4.
- CI runs on Ubuntu 24.04; documentation must not imply all Ubuntu releases are tested.
- `DBTUNE_REPOSITORY` remains unsupported.
- `DBTUNE_DOWNLOAD_BASE` is only a controlled mirror/test transport and never changes upstream attestation policy; `file://` is non-production.
- Audit classification exits are PASS/FINDINGS `0`, UNKNOWN `2`, and ERROR `1`; technical failures may use the established `64+` range.
- Private vulnerability reports use GitHub Private Vulnerability Reporting.
- Tags are never force-moved and failed verification gates are never bypassed.
- Do not add runtime features or change tuning rules in this release preparation.
